# Workflow Template Usage: Playwright CI

How to configure and wire up the Playwright CI workflow for a new client engagement.

## Prerequisites

Before creating the workflow, the client's Playwright directory must exist and be functional:

- `clients/client-[slug]/playwright/` scaffolded from `forge/templates/playwright/`
- `package-lock.json` present (generated by running `npm install` locally)
- Tests passing locally against the target environment

## Steps

### 1. Copy the template

```bash
cp forge/templates/workflows/playwright.yml \
   .github/workflows/client-[slug]-playwright.yml
```

### 2. Replace all placeholders

Search the file for `REPLACE` — there are 8 instances. Update each one:

| Placeholder | Replace with |
|---|---|
| Workflow `name` | `"Client [Name] — Playwright Tests"` |
| `push.branches` / `pull_request.branches` | Client's branch strategy (usually just `main`) |
| `working-directory` | `clients/client-[slug]/playwright` |
| `node-version` | Client's required Node version (default: `20`) |
| `cache-dependency-path` | Same path as working-directory + `/package-lock.json` |
| `BASE_URL` secret name | `PLAYWRIGHT_BASE_URL_[SLUG]` — generated automatically by the onboard script |
| Artifact `name` | `playwright-report-[slug]` |
| Artifact `path` | `clients/client-[slug]/playwright/playwright-report/` |

### 3. Set the GitHub secret

In the GitHub repo settings → **Secrets and variables → Actions → New repository secret**:

| Name | Value |
|---|---|
| `PLAYWRIGHT_BASE_URL_[SLUG]` | The base URL of the environment under test (e.g. `https://staging.client.com`) |

The onboard script generates the correct namespaced name automatically (e.g. `PLAYWRIGHT_BASE_URL_ACME`). Using a namespaced name avoids secret collisions when multiple clients share the same repo.

### 4. Commit and push

```bash
git add .github/workflows/client-[slug]-playwright.yml
git commit -m "ci: add Playwright workflow for client-[slug]"
git push
```

The workflow will trigger on the next push or pull request to `main`.

### 5. Verify

- Go to the repo's **Actions** tab on GitHub
- Confirm the workflow runs and tests pass
- On completion, the HTML report will be available under **Artifacts** on the run summary page

## Notes

- **Browsers:** The template runs Chromium only by default. See the multi-browser section below for how to enable Firefox and WebKit.
- **Artifacts:** Reports are retained for 30 days. Adjust `retention-days` if the client has compliance requirements.
- **Multiple environments:** To run against both staging and production, duplicate the workflow file and point each at a different secret.
- **Secret naming:** The onboard script always generates `PLAYWRIGHT_BASE_URL_[SLUG]` (e.g. `PLAYWRIGHT_BASE_URL_ACME`). All clients in this repo follow this convention — no collisions possible.

## Multi-Browser Coverage (Optional)

The template ships with a commented-out `strategy.matrix` block that enables Chromium, Firefox, and WebKit as parallel CI jobs. It is off by default.

### When to enable it

Offer multi-browser coverage only when a client explicitly asks for it or when their user base has meaningful non-Chromium traffic. Most early-stage clients do not need it.

### Cost tradeoff

| Configuration | Minutes per push | Runs/month at 2,000 min cap |
|---|---|---|
| Chromium only (default) | ~3–5 min | ~400–600 |
| + Firefox | ~6–10 min | ~200–300 |
| Chromium + Firefox + WebKit | ~9–15 min | ~130–220 |

These are estimates. Actual cost depends on test count and suite duration. Monitor usage under **Settings → Billing** on GitHub.

### How to enable

1. Open the client's generated workflow file (`.github/workflows/client-[slug]-playwright.yml`)
2. Uncomment the `strategy` block:
   ```yaml
   strategy:
     matrix:
       browser: [chromium, firefox, webkit]
     fail-fast: false
   ```
3. Change `chromium` to `${{ matrix.browser }}` in three places:
   - `npx playwright install --with-deps chromium` → `${{ matrix.browser }}`
   - `npx playwright test --project=chromium` → `${{ matrix.browser }}`
   - Artifact `name`: `playwright-report-client-[slug]-chromium` → `playwright-report-client-[slug]-${{ matrix.browser }}`
4. If the client uses the publish-report workflow, update its artifact reference to pick up one of the matrix artifacts (typically chromium — the publish step is browser-agnostic).

### Do not enable by default on existing clients

Enabling the matrix on a client who did not ask for it increases their CI cost without delivering value. Always confirm with Luke before enabling on an active client workspace.

## Part 2: GitHub Pages Reporting (Optional)

Publish a live HTML test report to GitHub Pages so clients can always access their latest results at a stable URL.

> **⚠️ Free-Tier Constraint — Read Before Promising a Client a URL**
>
> GitHub Pages is only available on free-plan repos that are **public**. There is no way to keep the main branch private and serve Pages on GitHub Free — it's the entire repo or nothing. Options:
>
> - **Make the repo public** — acceptable if test code isn't sensitive, but exposes all client code
> - **Upgrade to GitHub Pro/Team** (~$4–$9/mo/user) — enables Pages on private repos
> - **Defer Pages** — use the Actions artifact download as a fallback until revenue supports Pro
>
> Do not promise a client a Pages URL until this decision is made.

### Published URL pattern

```
https://[org].github.io/[repo]/client-[slug]/latest/
```

Tell a client: _"Your latest test results are always at `https://Northform-qa.github.io/[repo]/client-[slug]/latest/`"_

### Steps

#### 1. Enable GitHub Pages on the repo

Repo → **Settings → Pages → Source** → set to **Deploy from a branch** → branch: `gh-pages`, folder: `/ (root)`.

The `gh-pages` branch is created automatically on the first workflow run — you do not need to create it manually.

#### 2. Copy the publish-report template

```bash
cp forge/templates/workflows/publish-report.yml \
   .github/workflows/client-[slug]-publish-report.yml
```

#### 3. Replace all placeholders

Search the file for `REPLACE` — there are 4 distinct replacements:

| Placeholder | Replace with |
|---|---|
| Workflow `name` | `"Client [Name] — Publish Report"` |
| `workflow_run.workflows` value | Exact `name:` field of the client's playwright workflow |
| Artifact `name` | Must match the artifact name in the playwright workflow (e.g. `playwright-report-acme`) |
| `client-SLUG` token (×4) | `client-[slug]` (e.g. `client-acme`) |

> **The `workflow_run.workflows` value must be an exact string match** to the `name:` field in the client's playwright workflow file. If the name is `"Client Acme — Playwright Tests"`, that string must appear verbatim here.

#### 4. Commit and push

```bash
git add .github/workflows/client-[slug]-publish-report.yml
git commit -m "ci: add Pages publish workflow for client-[slug]"
git push
```

The publish workflow fires automatically after the next Playwright run completes (pass or fail).

#### 5. Verify

- Go to **Actions** tab → confirm the publish workflow ran after the Playwright workflow
- Go to the Pages URL: `https://[org].github.io/[repo]/client-[slug]/latest/`
- The root dashboard at `https://[org].github.io/[repo]/` lists all client reports and updates automatically on each publish
